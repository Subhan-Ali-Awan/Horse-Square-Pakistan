================ SLIDE 3 ================
 - Introduction
 - CampusConnect is a dedicated web platform built exclusively for Minhaj University  requiring an official registration number and campus email to sign in. This ensures a verified, safe community. The platform brings many campus services selected via student surveys into one unified web application, built on the MERN stack (MongoDB, Express, React, Node.js). The application is expected to sit beside the existing CMS.
================ SLIDE 4 ================
 - Problem Statement
 - Minhaj University Lahore's current CMS only handles academic administration and completely lacks student-to-student community features. This causes, students to rely on unverified, unmoderated social media channels (Instagram and Facebook community pages), which put them at risk of being exposed to inappropriate content and may prevent meaningful alumni networking. This absence of a centralized, secure platform also leaves students struggling with disorganized daily campus servicessuch as petitions and lost-and-found, as well as limited, expensive food options.
================ SLIDE 5 ================
 - Literature Review
 - CampusConnect draws inspiration from existing platforms while addressing gaps none of them individually solved.
 - Reddit & Stack Overflow: Inspired the main idea of "Minhaj being a community" and the threaded discussion structure  CampusConnect uses the same nested reply format adapted for a campus context.
 - Foodpanda: The food ordering workflow (menu browsing  cart  order tracking) was redesigned and adapted for a single campus delivery point.
 - InDrive: The rider's shared open ticket pool model was inspired by InDrive's ride-ticket system, adapted for campus food delivery.
 - COMSATS Plus: The concept of bundling multiple university services into one platform was directly inspired by this existing campus super-app.
 - Key Research Finding: No existing platform and LMS/CMS portals implemented or offered by other Universities; combines verified identity, AI content moderation, peer discussion, food ordering, and career networking into one campus-specific solution.

================ SLIDE 7 ================
 - Goals, Objectives & System Modules
 - The primary goal of CampusConnect is to exist with the university's existing academic CMS and establish a moderated, virtual community exclusively for Minhaj's students. To achieve this objective, the platform integrates multiple daily campus services into a single hub, allowing users to safely engage in AI-moderated peer discussions, seek career mentorship from alumni, and submit formal petitions to the administration. Furthermore, the system aims to solve everyday logistical challenges by providing dedicated, centralized modules for tracking lost items, viewing shuttle routes, and ordering food from local vendors directly to the campus gates.

================ SLIDE 13 ================
 - Key Innovation - AI Content Moderation
 - CampusConnect is the ONLY platform in the comparison in its scope that checks content before it is
 - published  and it understands both English AND Roman Urdu.
 - User Submits Post
 - Built-in Word List Check
 - if clean
 - Groq LLM Check
 - Post Published Live
 - Moderation Queue
 - if flagged
 - if flagged
 - ?  Two-layer pipeline: a fast built-in word list runs first; if the post passes, it is forwarded to the Groq language model API for deeper analysis.
 - ?  Google Gemini serves as a second moderation model  used alongside Groq for higher confidence decisions.
 - ?  Fallback safety: if both AI services are unavailable, the built-in word list still runs  posts are never published unchecked.
 - ?  Flagged posts are hidden immediately; a reason is stored for the moderator. Users are NOT told which rule was triggered, preventing circumvention.
 - ?  Moderators can restore wrongly flagged posts OR issue on-screen warnings the user must acknowledge before using the platform again.
 - ?  Tested successfully: offensive content in English and Roman Urdu both detected; clean content passes in under 4.07 seconds (well within the 5-second requirement).

 - Implementation
 - Development Approach
 - ?  Module-by-module development  each module has its own client pages, API routes, and database model. New features added without breaking existing ones.
 - ?  API-first: every route built and tested in Postman before the React page was built  if a page failed, the server was ruled out.
 - Request Processing Pipeline
 - Security (Helmet/CORS)    Body Parsing    Sanitization ($-operator removal)    Token & Role Check    AI Moderation (if content)    Controller    Database
 - Project Folder Structure
 - ?  Two-root structure: /client (React, Tailwind, Socket.io-client) and /server (Express, Mongoose, Socket.io, AI SDKs)  each with its own package.json and environment variables.
 - ?  Single translation stub function wraps all visible text strings  ready for Urdu localization without rewriting pages.
 - ?  Coding standards: clear naming, true modularity, server-side trust (totals and counts always computed server-side), secret management via .env.
================ SLIDE 15 ================
 - Real-Time Notifications & Features - Socket.io
 - ?  Order placed by student  vendor dashboard updates instantly, no page refresh required. Achieved via Socket.io event broadcast to the vendor's connected socket.
 - ?  Rider claims ticket  order status pushed live to the student's order tracker AND the vendor dashboard simultaneously.
 - ?  Petition signed  signature count updates in real time for everyone currently viewing that petition.
 - ?  Moderation action  hidden content disappears from all open pages immediately when the moderator hides it.
 - ?  Notifications bell  unread count updates automatically without polling. Browser push notifications via Web Push VAPID alert users even when the site is not open.
 - ?  Measured performance: Live update delivery time = 100ms average (requirement was < 2 seconds  exceeded by 20x).

================ SLIDE 16 ================
 - Campus Canteen - Food Ordering Module
 - ?  Students browse open restaurants, view menus, add items to a cart, and place an order with a contact number to the campus main gate.
 - ?  Order total is calculated server-side only  the browser total is never trusted. This prevents price manipulation.
 - ?  Each order is assigned a unique serial number on creation.
 - ?  Vendor dashboard: receives new orders via Socket.io (no refresh needed). Vendor accepts or rejects, then marks: Pending  Accepted  Preparing  Ready  Picked Up  Arrived  Completed (7 states).
 - ?  Rider Dashboard: a shared campus-wide ticket pool; any rider can claim any accepted order. Claiming is atomic  if two riders attempt simultaneously, only one succeeds; the other is told the ticket is gone. Student's number is not shared with riders to implement a no-trust policy.
 - ?  Closed restaurants are automatically hidden from student view the moment the vendor closes the restaurant on their dashboard.
 - ?  Order State Transition: 7 states involving 3 actors (Student, Vendor, Rider). "Cancelled" is a dead-end state only reachable if the vendor rejects.
================ SLIDE 17 ================
 - Testing & Evaluation
 - Use Case Testing
 - ?  22 test cases executed  12 student path, 10 vendor/rider/admin path.
 - ?  All 22 passed including sign in, order lifecycle, moderation, petition, bookmarks, role-based access, and sign out.
 - Extension / Edge Case Testing
 - ?  12 extension scenarios tested all passed. Key cases: wrong password (no token issued); deleted account (all token requests denied); offensive Roman Urdu caught by built-in word list; duplicate petition signature rejected; two riders claiming same ticket (only one succeeds); moderation service unreachable (built-in filter still runs); closed restaurant stops new orders.
 - Boundary Value Analysis
 - ?  15 field boundaries tested  all passed. Including: empty fields, duplicate emails/reg numbers, image size limit (50MB), injection characters ($-operator stripped), role validation, cart cannot be empty.

================ SLIDE 20 ================
 - Conclusion & Limitations
 - Conclusion
 - ?  CampusConnect successfully delivers a verified, moderated, and feature-complete campus community platform for Minhaj University Lahore.
 - ?  All 16 modules are implemented, tested, and deployed on a live production environment  accessible via web browser on any device.
 - ?  The AI moderation layer effectively screens English and Roman Urdu content with a reliable fallback mechanism  no post is ever published unchecked.
 - ?  All performance targets were met or exceeded; all 22 use cases and 12 extension scenarios passed during testing.
 - ?  The platform fills an unmet need at Minhaj University  replacing unverified social media groups with a structured, safe, and centralized hub.
 - Current Limitations
 - ?  Bus routes are currently hardcoded  not updatable by the transport office without developer involvement.
 - ?  No real-time GPS tracking for buses (routes are static schedules).
 - ?  Payment for canteen orders is cash on delivery  no online payment yet.
 - ?  Platform is English-only (Urdu translation stub is in place but not yet populated).
 - ?  No automated test suite  testing was manual; automated tests are recommended before scaling.
